# Developer guide

Use the development app to change and test NabeCMS itself. If you are building a site with the published CMS, start with the [Quick Start](./getting-started.md).

## Repository structure

| Location | Role |
| --- | --- |
| `packages/nabecms-core` | Worker API, authentication, data processing, and shared types |
| `packages/nabecms-admin` | Admin UI |
| `packages/nabecms` | Published package combining the Worker and prebuilt Admin UI |
| `packages/nabecms-cli` | Configuration checks, migrations, and runtime migration bundle generation |
| `packages/create-nabecms` | App initializer |
| `packages/dev` | Integrated Worker and Admin UI environment for developing NabeCMS |
| `examples/basic` | Reference app using the published packages |
| `docs` | User and developer documentation |

## Development environment

Run the Worker and Admin UI together when changing API behavior or editing flows. Set up dependencies and local secrets from the repository root.

```bash
pnpm install --frozen-lockfile
cp packages/dev/.dev.vars.example packages/dev/.dev.vars
```

Generate secrets as described in the [Quick Start](./getting-started.md#configure-local-secrets).
After filling in `packages/dev/.dev.vars`, prepare the database and start the app.

```bash
pnpm db:migrate:local
pnpm dev
```

The Worker runs at `http://localhost:8787`, with the Admin UI at `/admin/`.
During development, the Worker connects to the Admin UI's Vite dev server.

## Reference app

`examples/basic` is the reference implementation of an app generated by the initializer.
The workspace links packages locally, so build the Admin UI first.

```bash
pnpm build
cp examples/basic/.dev.vars.example examples/basic/.dev.vars
```

Configure the secrets, then run these commands.

```bash
pnpm -C examples/basic run nabecms:migrate --local
pnpm -C examples/basic run typecheck
pnpm -C examples/basic run dev
```

Use this app to check how a change affects people who install NabeCMS. Its scripts run with `pnpm -C examples/basic run <script>`, and its deployment follows [operations and deployment](./operations.md).

## Verification

Choose checks based on what changed. Use `pnpm verify` for the combined source checks, then exercise the relevant browser, package, or documentation path.

| Command | Checks |
| --- | --- |
| `pnpm test` | Regression tests for Core, the Admin UI, CLI, starter, and packaging tools |
| `pnpm verify` | Build, lint, formatting, type checks, regression tests, and configuration checks |
| `pnpm admin:test:e2e` | Main Admin UI actions in a browser against a dedicated local Worker |
| `pnpm package:smoke` | Five tarballs, plus app generation, installation, type checking, configuration checks, migration, startup, setup, sign-in, and a deployment dry run outside the repository |
| `pnpm security:audit` | Known vulnerabilities in production dependencies |
| `pnpm docs:build` | Documentation build and internal links |

Run `pnpm build` before `pnpm package:smoke`.
The browser and package smoke tests remove temporary apps and local databases when they finish.
Verify deployment on Cloudflare and installation from npm for the first release and when the environment changes.

If you change the schema or migration chain, use the D1 integration tests to check that a fresh database and existing data both migrate correctly.

## Maintain the starter

`packages/create-nabecms/template/basic` and `examples/basic` share configuration, SQL, and the runtime migration bundle.
`pnpm starter:test` checks that they stay in sync.
D1 integration tests also compare the resulting schemas after applying the development and public migration chains.

For package entry points and options, see the [configuration reference](./configuration.md).
For schema extensions, see [data management](./data-management.md#extend-the-schema).
