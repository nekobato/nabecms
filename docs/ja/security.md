# セキュリティ

アプリを利用者に開放する前に、ログインできる人、配信できるコンテンツ、ログを閲覧できる人を決めます。
配備時のコマンドは[運用とデプロイ](./operations.md)に記載しています。

## シークレット管理

本番環境では、シークレットを Cloudflare Secrets に登録します。
ローカルとは異なる値を使い、用途ごとに別のランダム値を生成します。
初期化前のアプリでは、`BOOTSTRAP_SECRET` を知っている人が最初の管理者を作成できるため、値を厳重に保管します。
漏えいした値は速やかに交換します。
設定が必要な値と保存先は[環境変数と Secrets](./cloudflare.md#環境変数と-secrets)で確認できます。

## ローカル認証と Better Auth session

利用者はメールアドレスとパスワードでログインします。
保存するパスワード情報は bcrypt のハッシュです。
管理 API のトークンは有効なセッションに結び付いているため、ロール変更でセッションが失効するとトークンも使えなくなります。
Super Admin のユーザー情報を変更できるのは Super Admin だけです。

メールアドレスの変更とパスワードの再設定はアカウントの所有者が行います。
本人へ一回限りの再設定リンクを届けるには[認証メール](./email.md#パスワードを再設定する)を設定します。
ユーザー更新時の制約は[Admin API のユーザー](./api/admin.md#ユーザー)を参照します。

リバースプロキシを使う場合は `Origin` と `Sec-Fetch-Site` を Worker に転送します。
HTML フォームから送信できる認証系の変更リクエストでは、これらのヘッダーを使って別のオリジンからの操作を拒否します。
利用できる認証方法とルートは[Admin API の認証モデル](./api/admin.md#認証モデル)に記載しています。

## Contents API の公開境界

配信対象から外すモデルやフィールドには `isPrivate` を設定します。
API キーでモデルへのアクセスを許可しても、非公開モデルを配信できるようにはなりません。
個別取得や他のエントリーからの参照での扱いは[Contents API の公開条件](./api/contents.md#キャッシュ方針)を参照します。

## API Key

配信用のキーはシークレットとして保管します。
連携先ごとにキーを発行し、`permissions` と `allowedModels` を必要な範囲に絞ります。
キーを入れ替えたら旧キーを失効させます。
発行と管理は[管理画面の API Keys](./admin/index.md#api-keys)から行います。

## 招待（Invites）

招待先の利用者に必要な権限を持つ通常ロールを作成します。
標準の Admin ロールは用意されておらず、`system.super-admin` などのシステムロールは招待では付与できません。
既存ユーザーの権限はユーザーの編集で変更します。

招待リンクは一度だけ使えます。
コピーしたリンクを共有する場合は、招待した相手だけが受け取れる手段を使います。
リンクの送信と再生成は[認証メール](./email.md#招待を送る)、使用できなくなった招待への応答は[Admin API の招待](./api/admin.md#招待-invites)を参照します。

## レート制限

本番では[二つの Rate Limiting バインディング](./cloudflare.md#固定の-route-と-binding)を設定します。
バインディングに障害がある場合、対象の操作には `503 AUTH_RATE_LIMIT_UNAVAILABLE` を返します。
ログインの試行は、二つのログインルートを合わせて同じメールアドレスにつき 60 秒に 10 回です。
それ以外の保護対象は、ルート、トークン、操作する利用者、再設定用の識別子など、操作ごとに定めた単位で 60 秒に 5 回です。
上限を超えると `429 AUTH_RATE_LIMITED` と `Retry-After: 60` を返します。

バインディングには変換済みの識別子を渡します。
レート制限ログには操作、バインディング、結果、ステータス、リクエスト ID を記録し、メールアドレスやトークンは記録しません。
Cloudflare のカウンターは拠点ごとで更新の反映に差があるため、この制限は不正な試行を抑える用途に使います。
詳細は[Workers Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)を参照します。

## メディア公開

R2 の公開アクセスと `r2.dev` は無効にし、バケットのカスタムドメインは設定しません。
ファイルは Worker のメディアルートを経由して配信します。
Worker がリクエストごとに公開状態を確認し、下書きやアーカイブ済みのファイルには認証とメディア権限を求めます。
アップロードできるファイルは[Admin API のアップロード要件](./api/admin.md#運用メモ)、削除後の配信と R2 の扱いは[メディアの運用](./operations.md#メディアの運用)を参照します。

## 監査ログ

操作ログはエントリー、モデル、設定への変更を記録します。
エントリーの変更とその操作ログは同時に確定します。
認証ログはローカルログインの結果と招待の受諾を記録します。
どちらも `logs:*:read` を持つ利用者が[ログ画面](./admin/index.md#ログの閲覧と検索)で閲覧できます。

ログには操作した人の ID、日時、結果、変更の概要を保存します。
エントリーの本文はリビジョンに保存し、閲覧にはエントリーの権限が必要です。
認証情報、リクエストの本文、メールアドレス、IP アドレス、セッション ID はログに保存しません。
応答の項目と検索条件は[ログ API](./api/admin.md#監査ログ-認証ログ)に記載しています。

## ログの保持期間と自動削除

保持期間は操作ログと認証ログに適用します。
エントリー、リビジョン、セッション、Workers Logs はそれぞれ別に管理します。
日次処理は実行開始の UTC 時刻から保持日数を引き、その時刻より前のレコードを削除します。
設定を読み取れない場合や設定の検証に失敗した場合は削除を中止し、件数の上限や障害で残ったログは次の実行で処理します。

保持期間を短くすると、保存済みの古いログも削除対象になります。
変更は[ログ管理](./admin/index.md#ログ管理)、実行間隔と障害対応は[ログの定期削除](./operations.md#ログの定期削除)を参照します。
