# アーキテクチャ

## 全体像

一つの Cloudflare Worker で API と管理画面を提供します。
Core は Hono で API を構成し、管理画面は Vue、Vite、Element Plus で実装しています。
本番で必要なリソースとバインディング名は[Cloudflare の前提と設定](./cloudflare.md)、各実装の場所は[リポジトリ構成](./developer.md#リポジトリ構成)を参照します。

## リクエストフロー

管理画面は Better Auth のセッション Cookie を短時間有効な管理 API トークンに交換し、そのトークンでデータを編集します。
外部のクライアントは API キーを使って Contents API からコンテンツを取得します。
どちらの API でも、権限の検査を済ませてから対象の処理に進みます。
認証方法と応答の規約は[API 概要](./api/index.md)に記載しています。

CMS のデータは D1、メディアのファイルは R2 に保存します。
メディアは Worker が公開状態と権限を検査してから配信します。
公開範囲は[メディア公開](./security.md#メディア公開)を参照します。

## データモデル

モデルはエントリーの項目を定義します。
保存した内容はリビジョンに残るため、読者には公開済みの版を見せながら、編集者は別の下書きを更新できます。
エントリーのフィールドにはメディアや他のエントリーを指定でき、Contents API は[参照先も応答に含められます](./api/contents.md#relation-展開)。

テーブル、カラム、制約の定義は[Core のスキーマ](https://github.com/nekobato/nabecms/blob/main/packages/nabecms-core/src/database/schema.ts)を参照します。

## 更新の一貫性

エントリーを更新するときは、リビジョン、公開する値、操作ログを D1 で同時に確定します。
一括公開も選択したエントリー全体を一度に確定します。
書き込みに失敗した場合はまとめて取り消します。
応答を受け取れなかった場合は、[Admin API の再試行の規則](./api/admin.md#entry-write-の再試行と-idempotency)に従って結果を取得できます。

初期化、招待受諾、パスワード再設定でも、関連するデータベースの変更を一度に確定します。
[マイグレーション](./data-management.md#マイグレーション)は、SQL と適用履歴を同じバッチで確定します。

## coreとアプリの境界

NabeCMS が CMS のスキーマ、API、認証、管理画面を提供します。
Worker の入口、配備設定、アプリ固有のデータは利用側のアプリが管理します。
本体のスキーマ変更から独自データを切り離すには、[スキーマの拡張手順](./data-management.md#schema-の拡張)に従ってテーブルを追加します。
